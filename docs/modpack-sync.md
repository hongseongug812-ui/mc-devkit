# 콘텐츠 제작팀 모드팩 동기화

MC DevKit 1.8.0에서 호스트와 참가자 모두 데스크톱 앱을 사용합니다. 공식 런처, CurseForge, Modrinth의 실제 게임 디렉터리를 연결할 수 있습니다.

## 호스트

1. 홈에서 서버·Minecraft 버전별 프로필을 만듭니다. 게임 버전이 바뀌면 기존 월드를 직접 전환하기보다 새 프로필을 만들어 분리하세요.
2. 프로필의 **모드팩** 탭에서 참가자 로더를 선택합니다. 배포한 로더는 그 모드팩에서 고정됩니다.
3. 기본 `client-mods` 폴더에는 참가자에게 필요한 `.jar`만 넣습니다. 제작 모드와 Fabric API 등 클라이언트에 필요한 의존 모드를 함께 넣으세요.
4. 서버에서 교체한 공용 모드를 바로 배포하려면 **서버 mods 폴더를 배포 원본으로 사용**을 선택하고 파일 규칙을 입력합니다. 예: `our-content-*.jar, fabric-api-*.jar`. `*`는 파일명 안의 모든 문자이며 쉼표로 구분합니다. 서버 전용 모드는 이 규칙에서 제외하세요.
5. **폴더 변경 시 자동 배포**를 켜고 **모드팩 배포**를 누릅니다. 이후 원본 폴더의 `.jar`를 교체하거나 삭제하면 새 배포를 만듭니다. 버전이 붙은 파일을 교체할 때는 구버전 파일도 원본 폴더에서 제거하세요.
6. 상단 **터널 켜기**로 DevKit 관리 서버의 공유 주소를 만들고 **참가 링크 복사**로 팀원에게 전달합니다. 직접 공개한 HTTP(S) 관리 서버 주소도 사용할 수 있습니다.

Minecraft 플레이에 사용하는 playit 주소와 DevKit의 모드 다운로드용 HTTP(S) 공유 주소는 서로 다릅니다. 호스트 앱과 공유 터널이 실행 중이어야 참가자가 받을 수 있습니다. 임시 공유 터널을 다시 시작하면 주소가 바뀌므로 새 참가 링크를 전달하세요. 참가자가 동일 서버·게임 폴더로 다시 참가하면 주소와 토큰이 갱신됩니다.

## 참가자

1. 사용할 Minecraft 버전과 Fabric / Forge / NeoForge 로더를 런처에서 설치합니다.
2. 서버·버전마다 별도 게임 인스턴스를 사용합니다. 공식 런처는 **설치 설정 → 게임 디렉터리**로 분리할 수 있고 CurseForge / Modrinth는 프로필별 게임 폴더를 사용합니다.
3. MC DevKit 홈의 **서버 참가**에 링크를 붙여넣고 런처를 선택합니다.
4. **게임 폴더 선택 · 참가**에서 `mods`의 상위 게임 폴더를 선택합니다.
5. 앱은 첫 동기화 후 실행 중 15초마다 배포를 확인합니다. 연결이 끊기면 오류가 표시되고 다음 주기에 다시 시도합니다. 앱을 닫으면 트레이에 남아 동기화를 계속하고 **완전 종료**하면 중지됩니다.

게임이 실행 중이면 적용을 기다립니다. 게임을 종료한 뒤 동기화가 끝났는지 확인하고 다시 실행하세요. **참가 해제**는 자동 동기화 연결만 없애며 설치된 모드와 백업은 남습니다.

## 파일 보호와 복구

- 크기와 SHA-256을 검증한 파일을 임시 폴더에 모두 다운로드한 후 교체합니다. 다운로드 실패는 현재 모드팩을 바꾸지 않습니다.
- 앱이 이전에 설치한 파일만 교체·삭제합니다. 개인 모드와 이름이 겹치거나 관리 파일을 사용자가 수정했으면 동기화를 중지하고 해당 파일을 표시합니다. 파일을 별도 위치로 옮기거나 새 게임 인스턴스를 선택해 해결하세요.
- 교체 전 파일은 게임의 `mods/.mc-devkit-backups/<배포 작업 ID>/`에 보관하며 참가 카드에 최근 백업 경로를 표시합니다. 백업은 자동 삭제하지 않습니다.
- 교체 중 실패하면 이전 파일로 되돌립니다. 앱이 종료돼 작업 기록이 남았으면 다음 동기화에서 복구한 뒤 다시 진행합니다.
- 수동 복원은 자동 동기화를 중지하고 게임을 종료한 뒤 백업 파일을 `mods`로 복사해서 수행합니다. 백업의 `previous-manifest.json`을 `mods/.mc-devkit-sync.json`으로 복원해야 관리 상태도 일치합니다. 첫 설치의 이전 manifest가 `null`이면 해당 상태 파일을 제거합니다.

서버에서 변경한 모드를 다른 Minecraft 버전용으로 자동 변환하거나 빌드하지는 않습니다. 제작 모드는 해당 버전용으로 빌드한 `.jar`를 배포해야 합니다. 게임 버전이나 로더가 바뀌면 새 서버 프로필과 참가자 게임 인스턴스를 만드세요. 런처나 로더 설치 자체는 자동화하지 않습니다.

## 서버 버전과 업데이트

설정 화면에서 종류별 공식 서비스의 버전 목록을 조회하고 새로고침할 수 있습니다. Paper는 PaperMC v3 Downloads Service의 안정 빌드를 사용하며 체크섬을 검증합니다. Vanilla는 Mojang, Fabric은 Fabric Meta에서 릴리스를 조회합니다. Arclight와 Cardboard도 각 프로젝트의 공개 릴리스 목록을 조회합니다.

Java는 게임 버전에 따라 준비합니다: 26.x는 25, 1.20.5와 1.21.x는 21, 1.18~1.20.4는 17, 1.17.x는 16, 이전 버전은 8입니다. 서버를 중지하고 **서버 실행 파일 업데이트**를 누르면 현재 저장된 버전의 실행 파일을 갱신하며 이전 실행 파일을 `runtime-backups`에 보관합니다.

## 검증

`npm test`로 파일 교체, 삭제, 충돌 보호, 다운로드 검증, 게임 실행 중 보류, 작업 중단 복구, 참가 관리, 실제 HTTP 인증·다운로드를 검사합니다. `node scripts/check-versions.js`는 외부 버전 서비스의 현재 응답을 검사합니다.

`node_modules/electron/dist/electron.exe scripts/ui-smoke.js`는 격리된 `.test-data/ui`에서 홈·설정·배포·참가 화면을 렌더링하고 설정 저장을 확인합니다. Electron 실행 전 `ELECTRON_RUN_AS_NODE` 환경변수를 해제해야 합니다. 기존 사용자의 프로필이나 Minecraft 서버를 실행하지 않습니다.
